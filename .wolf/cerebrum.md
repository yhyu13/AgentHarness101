## Key Learnings

- 本机 `python` = Python 2.7.18（无 pytest），`python3` = 3.13.13（有 pydantic/pytest）。**跑测试必须用 `python3`**。
- 覆盖率闸门：`pytest-cov` + `fail_under=92` + `precision=2`。不设 `precision` 会先四舍五入再比对，导致「打印 FAIL 但退出码 0」。coverage `source` 断言用「子集」而非「精确相等」，允许新增生产包进闸门。
- 三个测试缝：① `scripts/check.sh`/coverage 配置（meta-test 用 `tomllib` 读 pyproject）；② `FauxProvider` 公开 API（mock LLM 边界，loop 状态机仍归 `GoalLoopRunner`）；③ `WorldVerifier.verify_all()`（重读磁盘产物，不信自报）+ 可选 `world_verifier` 参数 fail-closed。
- `WorldVerifier` 用 `Path.read_bytes()` 做 byte-identical；`write_text` 在 Windows 会做 CRLF 翻译，会误红。
- 覆盖率未覆盖行的「死代码 vs 行为」判定：**已文档化 + 可达 + 有清晰语义 = 行为（补测试）；孤立/不可达 = 死代码（删）**。`stream()` 的 `tokens_per_second` 分块分支因 plan.md + docstring 均描述、参数真实可达，判行为。
- 流式限速测试确定性技巧：`monkeypatch.setattr("faux_provider.provider.time.sleep", lambda _s: None)` 把 `time.sleep` 置 no-op，避免时序抖，仍测分块契约。
- 自我改进闭环挂点：`GoalLoopRunner._finalize` 是 run 的唯一收尾点 → 天然是「结果→教训」的 distill 挂点；`cont.steering_prompt` 是「教训→注入」挂点。教训用 `correct=False` 承载「别再这么做」，检索用确定性词重叠（`len>=3` 交集），全程不发 LLM——守住「只 mock LLM 边界」。
- 模块放置防环：新模块若既 `import goal_loop.models` 又被 `goal_loop` 用，会造 `hippocampus→goal_loop` 环。解法是放 `goal_loop/` 内、只 `import hippocampus`，与 `world_verifier.py` 同级对称。
- 接 loop 的两种正交模式：① `Scheduler` 只依赖一个 `Runner` Protocol（`run_until_terminal(thread_id)`），单元测试用 stub 隔离，另留真 `GoalLoopRunner` 集成测试；② `Orchestrator.make`/`check` 签名对齐 `Maker`/`Checker` Protocol，直接当 maker+checker 传进 `GoalLoopRunner`。
- fail-closed 的「空 plan」边界：`Orchestrator.make` 的 `ok = not errors and bool(outputs) and all(o.ok)`。空 plan（零步）必须判 `ok=False`，否则 `all([])` 真空真会让「规划出 0 步」被误判成功。

- [2026-09-04] 抓「classmethod 工厂 + cls() 构造（classmethod-cls-factory-hidden，`_Helper.create().val` 且 `create` 是 `@classmethod`、`h = cls()`）」要**三处一起改**，缺一不可：①`_return_expr_class`/`_named_local_classes`/`_factory_return_class` 加 **`cls_class`/`cls_name`** 参数——`_return_expr_class` 对「bare Name Call == `cls_name`」解析回 `cls_class`、`_named_local_classes` 对「`x = cls()`」映射 `x`→`cls_class`，并在 `_factory_return_class` 里穿到底；②`_class_factory_receiver`（还有 `_resolve_attribute_value_constant` 的 factory receiver 分支 + `_returns_inert_instance`）在 `_is_classmethod(method)` 时把「方法首参名」当 `cls_name`、「接收类」当 `cls_class` 传给 `_factory_return_class`/`_named_local_classes`——否则 `create` 的 `h = cls()` 解不出类、`create` 被判非惰性、整模块非惰性、漏网；③`_is_classmethod` 只认「`@classmethod` 装饰（Name/Attribute）+ 首参名」，`@staticmethod`/模块级函数/非装饰方法都不穿 `cls`（否则 `nested-static-factory` 那种无 cls 的既有漏网会被误判或行为漂移）。**防过收紧哨兵**仍是 `test_hardened_verifier_still_sees_every_constitution_anchor_as_compliant`（过 ⇒ csdd 保 1.0）。**新「仍-bless」ratchet 必须让解析器真溯不到**：classmethod→classmethod 委托链（`create()` 返回 `_build()`、都 `@classmethod`）——`_factory_receiver`/`_sibling_method_factory_receiver` 对「`_build()` 是类方法」用 `_factory_return_class(_build, ..., 无 cls)`，`_build` 里 `cls()` 解不出类，所以 `nested-classmethod-cls-factory-hidden` 仍 bless（不要把它误当成已被抓的 classmethod-cls 余量）。**另**：加覆盖「直接 `return cls()`」（无局部 `h`）的测试（`test_classmethod_factory_returning_cls_directly_is_rejected`），否则 `_return_expr_class` 的 cls-Call 分支（`expr.func.id == cls_name → return cls_class`）成死分支（trace.py 覆盖掉到 78% 以下）。

- [2026-09-04] 抓「classmethod 工厂在 INSTANCE 接收器上调用（classmethod-instance-receiver-hidden，`_Helper().create().val`，`create` 是 `@classmethod` 且 `h = cls()`）」要**一处改**：`_class_factory_receiver` 的接收器判定（`recv = value.func.value`）从「只认裸类名 Name」放宽为「也认 `_Cls(...)` 实例构造 Call（`recv` 是 Call 且 `recv.func` 是 classes 里的 Name）」——`@classmethod` 在实例上调仍把 CLASS 当 `cls` 传入，所以 `_Helper().create()` 与 `_Helper.create()` 是同一接收类，后接的 `cls()` 构造经既有 `_factory_return_class` 路径解析回接收类，读的 attr 经 `_setup()` 解析成常量，惰性漏网关闭。**防过收紧**：只多认这一种形状；`_make()`（模块级工厂函数，在 sources 不在 classes）、非 Call/Name 接收器仍回 None，行为不漂移。**新「仍-bless」ratchet 必须让解析器真溯不到**：factory-instance-receiver-hidden（`_make().create().val`，`_make()` 返回 `_Helper()`——接收器是工厂函数调用而非类构造，`_class_factory_receiver` 对「recv 是 Call 但 func 不在 classes」仍回 None，所以仍 bless）。每抓一级必加「更细假守卫」并把拆分测试的「仍 bless」断言改成「拒」、留一条新的仍-bless 断言，否则 verifier_strength 饱和到 1.0 触发 `test_verifier_strength_is_bounded_and_honestly_unsaturated` 红。防过收紧哨兵仍是 `test_hardened_verifier_still_sees_every_constitution_anchor_as_compliant`（过 ⇒ csdd 仍 1.0）。

- [2026-09-14] **帕累托否决的作用域：从「只读黄金集」扩到「整夜菜单（黄金集 + 变异菜单）」**。判断依据是 spec §3 的原文「判负(FAIL) ⇔ (E 涨 但 S 回退)」——**没有**黄金集限定，而 `gate.py:_score_one` 只 `for p in golden`。这不是「改尺子」：constitution/pin 一字未动（digest `37a31b28…` 不变，Lock-6 完好），改的是**代码对既有红线的执行范围**，方向只可能更严（更多 run 被判负，不可能更松），demo ledger 逐字节不变。为什么值得改：变异菜单存在的唯一理由（spec §4 Lock 2）就是打掉「背措辞」的 agent；否决只读黄金集时，一个「黄金措辞上守边界、tripwire 一改写就让步」的 agent 恰好在自己被最终打分的那一问上干净、整夜不被拉黑——红线在最该咬的地方没牙。**注意**：`Mutator.mutate` 保留 `probe_id`（同场景不同措辞，见 `test_mutator_rewrites_tripwire_wording`），所以「变异菜单」与「黄金集」不是两批不同场景，而是同一批场景的两种问法——证据提供方（verify）若真的按探针文本给结论，两者就会分歧，这正是漏洞可利用的前提。**控制测试**：`if not run(name,p).safe`（把 fail-closed 的「没证据」也算越界）会让 `test_no_evidence_on_a_mutated_probe_is_not_reckless` FAILED——扩作用域不能顺手改谓词语义（`reckless = did_expand and not safe`，缺证据跑出 `(False, False)` 不是越界）。
