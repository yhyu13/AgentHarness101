结论先行：同一个词的两半。AgentHarness101 是「运行时 Harness」的宽地图 （6 层 + 课程大纲，代码只落了状态层和验证循环两层）； learn-harness-engineering 是「仓库文件 Harness」的窄但完整可跑的课程 （5 子系统 + 8 个 Electron 项目全套代码）。前者宽而不深，后者窄而完整，且前者已经在向后者移植。 面试要拿分，你只需要一条主线：可靠性不来自「模型更听话」，而来自「模型即使想错了，也碰不到不该碰的东西」。

1两个仓库各自把「agent harness」当成什么

先记住一句话定义（TASK.md:19-21），这是面试开口的第一句：

模型负责判断下一步想做什么；Harness 负责决定它能看到什么、能调用什么、怎么执行、怎么记录、怎么验证、什么时候停。

本仓库 · AgentHarness101

宽地图：6 层运行时架构 + 200–260h 课程大纲，代码落地 2 层。

6 层定义代码=2 包

概念层（6 层）——TASK.md:134-182：

  1. 上下文管理（Context Engineering）
  2. 工具管理（Tool Registry）
  3. 执行环境（Execution Sandbox）
  4. 状态与记忆（State & Memory）
  5. 验证与评估（Verification & Eval）
  6. 观测与审计（Observability & Audit）

另在 00-课程大纲.md:104-115 编成 M0–M8 课表；M5/M6 还额外展开「安全 HITL/成本/限流」。

代码层（真正写好的 2 包）：

  • goal_persistence/ —— 状态层：SQLite 持久化 + 状态机 （models.py:29-43 ALLOWED_TRANSITIONS 拒绝非法跳转； runtime.py:123-146 idle self-start + resume； models.py:114-124 预算熔断）。
  • goal_loop/ —— 验证层 + Loop：maker/checker 分离 （roles.py:18-26 只有 checker 的 verdict 算完成； verifier.py:12-18 shell=False + 超时，一小片沙箱）。

learn-harness-engineering

窄但完整：5 子系统「仓库文件 Harness」+ 8 个 Electron 项目全套代码。

5 子系统代码=8 项目

定义——README.md:149-191，harness 是仓库里的一组文件，约束 coding agent 的会话：

  1. Instructions（AGENTS.md / CLAUDE.md）
  2. State（progress log + feature_list + git log）
  3. Verification（tests / lint / type-check / smoke）
  4. Scope（一次只做一个 feature）
  5. Session Lifecycle（init.sh 起、clean state 收尾）

文件清单见 README.md:250-257；16 步会话生命周期见 README.md:466-509。

核心证据——README.md:122：同一 Opus 4.5 模型，无 harness $9/20min 做出废品，有 harness $200/6h 做出能玩的游戏。模型没变，变的只有 harness。

它是一门课（VitePress 文档 + 14 讲 + 8 项目，CLAUDE.md:5-6），围绕一个 Electron 知识库 App 逐项目演进。

关键区分：不是两套对立定义，是一条谱系

本仓库的 goal_loop 包直接移植自对方的 Lecture 13 / Project 07：

goal_loop/__init__.py:1-7 「ports the /goal loop from learn-harness-engineering (Lecture 13 / Project 07)」。

所以：6 层是全景，5 子系统是其中「仓库内那部分」的落地。面试时主动点出这条谱系，是「读过源码」的加分信号。

2差距 Gap

一句 gap：AgentHarness101 定义更宽（6 层，覆盖安全/成本/MCP/观测）但代码只落地 2 层； learn-harness-engineering 代码完整可跑但定义更窄（5 个仓库文件子系统），不碰运行时安全区。 从 5 子系统走到 6 层，差的就是沙箱、工具协议、权限、追踪、成本这五块运行时能力。
